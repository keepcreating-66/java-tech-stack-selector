日期：2026-11-04  
状态：开发前审阅稿；本文件是实施基线，不表示已开始开发或已授权公开发布。

## 1. 交付目标与固定决策

将现有工具交付为一个可以独立安装到 Claude Code 本地会话中的完整 Skill。用户通过自然语言或 `/java-tech-stack-selector` 发起任务，由 Agent 收集必要信息、调用确定性脚本生成工程，再按实际条件验证。

| 项目 | 本轮决定 |
| --- | --- |
| 产品名称 | Java Tech Stack Selector |
| 新 Skill 名称/目录 | `java-tech-stack-selector` |
| 新 Skill 首个候选版本 | `1.2.0-rc.1`，说明基于插件 1.1.0；验收后准备 1.2.0 正式包 |
| 首要目标宿主 | Claude Code 本地终端会话，支持项目级及个人级安装 |
| 第二宿主 | Cursor，执行兼容性验收后才声明支持 |
| 分发方式 | GitHub 本地安装 ZIP，以及 Agensi 上传 ZIP；使用同一核心和接口 |
| 原 VSIX | 保留现有交互及生成能力，改为调用共享核心；本轮不发布新 VSIX |
| 许可证 | 保留现有 MIT 声明与归属，本轮不改许可、不新增收费机制 |
| 商业与平台动作 | 准备免费首发材料；实际账号操作、上传、提交审核、公开发布不属于本轮开发动作 |
| 执行依赖 | 生成器运行基线 Node.js 22；工程编译目标 Java 17，构建使用 Maven 3.9.x |
| 安装方式 | 解压完整 Skill 文件夹；使用时不要求安装 VSIX、不要求克隆源码、不要求 npm install |

交付的是 `SKILL.md + scripts + references + examples`，不能只复制 Markdown 后就宣称具备工程生成能力。Claude Code 云端会话、Cowork、其他 Agent 不在首版兼容承诺内。

## 2. 当前代码依据与需要解决的问题

已检查的实现：

- `skills/tech-stack-selector/SKILL.md`：已有选型指导，但仍主要指引 VSIX 完成确定性生成。
- `vscode/src/generation/plan.ts`：已有纯规划函数 `planProject()`，能产出配置、提示词或工程文件集合。
- `vscode/src/generation/write.ts`：已有 `writeProject()`，检查目标冲突、路径及暂存写入。
- `vscode/src/core/schema.ts`、`validate.ts`、`capabilities.ts`：已有运行时结构与能力校验。
- `vscode/src/core/data.ts`：已有默认配置、三种业务预设和集中依赖版本表。
- `vscode/test/`：已有生产生成器测试、向导测试、六组 Maven 构建场景与网关冒烟脚本。
- `skills/tech-stack-selector/scripts/validate-config.sh`：实际只检查旧 Cursor 插件布局，不是业务配置校验器。

本轮解决四个缺口：脱离 IDE 的执行入口、独立可分发的生成脚本、跨宿主的任务指令、从安装到实际工程结果的验收。现有测试的存在不代表本轮已执行通过。

## 3. 首版功能范围

| 维度 | 必须支持 |

| 业务预设 | 企业管理、电商、AI 应用、自定义；AI 预设只生成基础后端，不包含模型接入或 RAG |

沿用现有配置的 `schemaVersion: 1`；首版沿用项目名与模块名规则，包括 2–20 个业务模块的限制。输出说明明确这属于当前生成器约束。

运行生成器不需要额外模型 API Key，模型推理由宿主 Agent 提供。

## 4. 用户流程与对话规则

1. 判断用户要做选型咨询、导出还是创建新工程。仅咨询时不创建工程。
2. 提取用户已给出的架构、场景、项目名、模块与组件，不重复询问已有明确答案。
3. 优先补齐架构、项目名、业务边界、输出模式与目标目录等影响结果的缺项。普通组件使用既有预设/默认值，并在预览中列明；架构无法合理推断时只问一个集中问题。
4. 预设只补默认值，用户明确值优先。电商不等于微服务；AI 预设不等于已支持模型集成。
5. 调用脚本做配置校验和只读规划，展示架构、组件、目录结构、文件数量、环境要求及目标路径。
6. 用户已明确要求按这些参数生成且授权覆盖范围未改变时继续执行；缺少关键选择或方案发生实质改变时再询问。预览不是强制的第二次授权门槛。
7. 在指定父目录下创建一个新的项目子目录。遇到已有目标、非法路径或不支持组件时停止写入，并给出具体错误。
8. 按用户请求与环境情况执行构建；网络访问及权限服从宿主机制。真实数据库验证只使用隔离测试资源或已明确授权的测试环境。
9. 汇报输出位置、文件状态、构建及运行状态、验证条件和下一步命令。

三种输出约定：`config` 只写 `tech-stack-config.json`；`prompt` 只写 `project-prompt.md`；`project` 输出完整工程。三种模式都使用新的项目子目录，保持与现有行为一致。

用户明确要求构建时实际尝试并报告结果；缺少环境或权限时不能标记通过，也不能自动安装全局依赖。运行服务验证与普通工程生成分开，生成器不自动启动 Docker 或长驻 Java 进程。

具体实施约束：

- 使用 npm 工作区和根锁文件管理共享开发依赖，迁移旧锁文件与安装说明；不引入第二种包管理器。
- 将平台无关逻辑迁入公共核心；QuickPick、IDE 文件选择、提示与 `vscode` import 留在 IDE 层。UI 选项类型与业务类型解耦。
- 共享核心是唯一维护源。使用项目级构建工具生成可读、未压缩的自包含 CommonJS 文本脚本；Node 标准库允许作为运行时依赖，不携带第三方运行时依赖。
- 为 VSIX 构建打包共享核心，不能让安装后的扩展依赖仓库外部目录或 workspace 软链接。
- 增加稳定的公共导出，测试使用公共接口，避免继续依赖原 `out/generation/` 内部路径。
- 保留旧 Cursor 命令入口并转接到新 Skill；旧 `tech-stack-selector` 不作为第二套同功能 Skill 自动发现。提供迁移说明，不自动删除用户已安装的旧副本。
- 原 `validate-config.sh` 按实际用途保留为旧布局检查，新增真正的配置校验命令，避免名称误导。

## 6. CLI 接口与结果协议

以同一个脚本支持下列子命令：

```text
node generate.cjs capabilities
node generate.cjs preset <enterprise-admin|e-commerce|ai-application>
node generate.cjs validate --config <文件或 ->
node generate.cjs plan --config <文件或 ->
node generate.cjs generate --config <文件或 -> --output-root <已有父目录>
node generate.cjs --version
```

`-` 表示从标准输入读取 JSON。对话中的配置可以通过标准输入传入，无须在 Skill 安装目录写临时配置。预设命令输出候选默认配置，不代表用户已经确认。

| 命令 | 行为 |
| --- | --- |
| capabilities | 输出真实可生成组件、配置版本和生成器版本 |
| preset | 输出相应业务默认配置，架构仍由用户需求决定 |
| validate | 校验 JSON 形状、命名、组件与字段组合；不写文件 |
| plan | 输出规范化配置、文件相对路径和数量；不写文件 |
| generate | 再次校验，安全写入新目录；不自动构建、不主动联网 |

成功结果使用 JSON，至少包含 `ok`、`command`、`generatorVersion`、`schemaVersion`。按命令补充规范化配置、项目目录、文件清单和数量。生成成功时明确返回 `build.status: not_run`、`runtime.status: not_run`。

失败结果包含 `ok: false`、稳定的错误 `code`、可读 `message` 和必要字段定位，不回显完整敏感配置。标准输出只输出协议 JSON；诊断信息进入标准错误。

退出码：0 成功；2 参数错误；3 配置错误；4 路径冲突或不安全；5 文件系统/内部错误。未知参数、未知命令和缺少参数均不能写入文件。`--help` 提供完整用法。

首版不增加 `--force`。不调用 shell 拼接用户输入。写入失败只清理本次创建的暂存内容，不能清理既有用户目录。

## 7. 本地安装与 Agensi 适配

### 本地安装

同一个 Skill 文件夹支持 Claude Code 的个人级 `~/.claude/skills/java-tech-stack-selector/` 与项目级 `.claude/skills/java-tech-stack-selector/`。文档提供两种手动安装方法，安装时遇到旧目录先提示备份/迁移，不自动覆盖。

Skill 主体采用通用 Agent Skills 字段及相对资源路径，不要求 Claude 专属工具名称。宿主差异仅保留必要说明，Cursor 路径与触发方式以实际验收为准。

### Agensi

当前官方 Docs 表明：平台按需返回文本，脚本原样保存到临时文件执行后移除；独立脚本不能依赖读取其他包文件。因此交付的 `generate.cjs` 必须把运行所需代码与模板自包含，用户配置和输出根目录通过参数/标准输入传入。

- 使用同一构建产物，不让 Agent 重写、删减脚本，也不依赖临时脚本旁存在 references 或模板。
- references 提供给 Agent 阅读；生成器本身不依赖它们。
- ZIP 采用一个顶层 `java-tech-stack-selector/` 文件夹，入口位于其下；不携带 node_modules、VSIX、JAR、二进制、软链接或系统杂项文件。
- 优先满足平台每个脚本逻辑部分小于 20 KB 的建议；模板数据与逻辑分开核算。这是文档建议，不能误称强制上传上限。阶段一测量并记录体积；若过大，先简化逻辑或按输出模式生成互不依赖的入口，保持同一核心维护。
- 按当前网站上传限额检查 ZIP：50 MB、1,000 文件；项目目标是远低于限额。
- 首版不编写自建 MCP 服务，不引入后台服务和托管费用。

本地测试增加“仅保留临时脚本、从不相关工作目录启动”的场景，模拟平台交付约束。该结果只证明适配设计可运行。Agensi 官方说明 listing 只有 live 后才会被实际服务，因此真实 MCP 取回与执行列为公开上线后的发布复验，不能提前标记已通过。

## 8. 依赖版本与兼容性策略

先用 1.1.0 的依赖表建立输出对比基线；当前源码的 Spring Boot 固定版本为 3.2.5，不能据此宣称是当前推荐版本。

在候选包冻结前核对 Spring Boot 与相关依赖的官方兼容及维护信息，形成明确的版本清单。必要的维护版本调整单独提交、单独执行构建矩阵，不与代码搬迁混在一起。不跨到 Boot 4、不改变 Java 17 编译目标。若发现无法在本轮兼容约束内解决的发布阻断问题，交付候选包与具体阻断说明，不能以迁移完成为由宣称可正式发布。

操作系统目标为 macOS、Linux、Windows；纯 Node 生成与文件保护测试通过三系统后才标注三系统支持。真实 Agent 调用及外部服务验证注明实际系统和版本，不将单机结果扩展为全部系统实测。

## 9. 验收矩阵与完成标准

### A. 核心、CLI 与安装包

- 现有生产生成器测试与向导测试通过；迁移过程中先比较相同配置生成的路径与文件字节内容。
- 若调整依赖版本，只允许有明确记录的差异；相同新配置经 CLI 和 IDE 入口生成的文件必须一致。
- 验证三种输出模式、JSON 文件/标准输入、预设、错误退出码及不支持项。
- 验证已有项目不变、路径越界拒绝、符号链接目标、并发同名创建、写入失败、中文与空格路径。
- 将发行 ZIP 解压到独立临时位置运行，不能借用仓库、原 node_modules、VSIX 或包外模板。
- `validate` 与 `plan` 不产生工程输出；取消或校验失败不创建目标工程。

### B. 实际工程构建

沿用并重新运行现有六场景：单体基础、模块化单体基础、带网关微服务、模块化单体组件组合、无网关微服务、单体组件组合。每组实际执行 `mvn -B -ntp clean verify`，记录配置、命令、退出码和日志。

现有矩阵主要使用 H2 测试，不代表真实 MySQL/PostgreSQL/Redis 已接通。补充代表性集成验收：

| 场景 | 要观察的实际结果 |
| --- | --- |
| MySQL + JPA + Spring Security | 健康检查、认证访问、CRUD 数据在真实数据库中读写 |
| PostgreSQL + MyBatis-Plus + Sa-Token + Redis | 登录及受保护 CRUD、真实数据库持久化、通过应用实际调用 Redis 客户端完成写读 |
| 网关 + 两个独立服务 | 两服务实际监听不同端口，网关请求到达对应后端 |

Redis 若当前示例无业务调用入口，在验收夹具中加入最小应用客户端调用，不为产品增加缓存业务。资源使用隔离测试库、随机测试端口和可识别测试键，只清理由本次创建的内容。没有授权的测试服务环境时记录待验收，不能把 H2 替代结果标为真实连接通过。

### C. Agent 行为

Claude Code 为首要验收宿主，Cursor 为第二宿主。记录宿主版本、系统、安装位置、触发请求、实际输出与命令证据。

- 每个宿主至少 5 个应该触发的请求、5 个相近但不应触发的请求；受控样本目标为 5/5 与 0/5，记录结果而不宣称普遍命中率。
- 必测实际任务：三种架构生成、仅导出配置、仅导出提示词、修改组件后生成、用户取消、目录冲突、不支持组件、缺少构建环境。
- 检查用户已给出的值不被重复询问或预设覆盖；不虚构按钮、不宣称未执行的构建成功。
- 对比无 Skill 与有 Skill 的一个相同任务，记录组件遵从、架构准确性和可复现差异，不要求输出文字相同。
- 生成工程不能依赖 VSIX；发布介绍仅列实际通过的宿主。

### D. 发布包

- Frontmatter、名称、相对链接、引用文件、示例 JSON、脚本语法及许可证检查通过。
- 包内无凭据、绝对开发机路径、测试产物、重复旧 Skill、隐藏系统文件和未声明联网行为。
- 构建两次后比较展开文件内容及 SHA-256 清单，确认构建不混入随机机器路径等内容。
- 准备真实演示请求与结果、环境要求、功能边界、安装与旧版迁移说明、Agensi 商品页草稿及兼容性表。

开发交付完成：本地 Skill 候选包存在、首要宿主实测通过、核心与 CLI 检查通过、六组构建通过、发行包独立执行通过，无已知阻断缺陷。任何未执行的三系统、第二宿主或外部服务检查必须列为待验收，限制对应发布声明。正式发布就绪还要求目标兼容性和真实服务检查完成；Agensi 真实加载在上线后复验。

## 10. 实施顺序、阶段出口与估算

| 阶段 | 工作 | 阶段出口 | 估算 |
| --- | --- | --- | --- |
| P0 基线与原型 | 运行原测试、保留基线产物；制作临时自包含脚本验证；检查版本风险 | 脱离 IDE、仓库与 node_modules 生成一个可构建单体；形成体积记录 | 0.5–1 天 |
| P1 共享核心 | 迁移公共代码、根构建入口、锁文件与 IDE 适配 | 三架构输出对比及向导回归通过 | 1–1.5 天 |
| P2 执行接口与发行构建 | CLI 协议、自包含构建、错误与写入边界、包检查 | 从解压包独立运行所有 CLI 模式 | 1–1.5 天 |
| P3 Skill 与兼容入口 | 主指令、引用、示例、旧命令转接、本地/Agensi 执行说明 | Claude Code 完整任务跑通，Cursor 开始实测 | 0.5–1 天 |
